Three words people mix up

Driver (minikube): where the node lives. Yours is docker, so the node is a container. Other drivers make a real VM.

Runtime (Kubernetes): what starts containers on a node. Yours is docker. The exam uses containerd.

Context (kubectl): a saved "which cluster, which user" line in ~/.kube/config. It is not a running thing.

The trap: docker ps on the Mac shows only one container (minikube). All the Kubernetes containers are inside it, in a second Docker engine, so you don't see them from outside.

Your outputs decoded

minikube profile list → DRIVER docker, RUNTIME docker

Driver docker = the node is a container. Runtime docker = inside that node, Kubernetes uses Docker to run pods.

docker ps → one container, image kicbase

kicbase is minikube's "Kubernetes in Container" base image. That single container is the node. Port mappings 127.0.0.1:32771→8443 is how your Mac reaches the API server (8443) inside it. →22 is SSH (used by minikube ssh).

kubectl get nodes -o wide → docker://29.2.1, IP 192.168.49.2

The CONTAINER-RUNTIME column is the inner engine. The 192.168.49.x address lives on a Docker network inside Docker Desktop's VM, which is why your Mac cannot reach it directly and needs the 127.0.0.1 port mappings.

--context docker-desktop → connection refused on 127.0.0.1:51288

The context exists in ~/.kube/config, but nothing is listening. Most likely Docker Desktop's built-in Kubernetes is switched off. So you have one live cluster (minikube), plus one dead context entry. (Earlier I said "two clusters" from the context list alone. Your output shows only one is alive.)
Optional tidy-up, not needed: kubectl config delete-context docker-desktop removes the dead entry. Check kubectl config get-contexts afterwards.

Prove it yourself (5 commands)

minikube ssh -- docker ps            # inner engine: k8s_* containers appear
minikube ssh -- sudo ls /etc/kubernetes/manifests   # static pod YAMLs of the control plane
minikube ssh -- sudo systemctl status kubelet --no-pager | head -5
kubectl config view --minify | grep server           # the 127.0.0.1 port mapping
docker port minikube                                 # compare with the line above

Practical rule: use the Mac for kubectl speed drills (YAML, imperative commands, RBAC, probes, rollouts, NetworkPolicy objects). Use the Killercoda CKA playground for anything about nodes, kubeadm, etcd, kubelet, certificates and upgrades.

Same Kubernetes, very different shape

The API objects (Pods, Deployments, Services) are identical. What changes is how many machines, who runs the control plane, and what surrounds the cluster.
